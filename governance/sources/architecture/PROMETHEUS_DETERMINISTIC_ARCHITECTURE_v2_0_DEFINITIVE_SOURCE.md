# 2. SOURCE AUTHORITY LATTICE

PROMETHEUS does not use a single naïve ranking for every question.

Authority is typed by domain.

## 2.1 Authority dimensions

### F — Factual authority
Controls claims about what was observed or physically occurred.

Priority:
`direct observation / competent measurement → independently verified evidence → derived model → assumption`.

### N — Normative/constitutional authority
Controls PROMETHEUS invariants and semantic boundaries.

Priority:
`Canon → ratified constitutional decision → architecture`.

### L — Legal authority
Controls enforceable legal meaning.

Priority:
`applicable law / competent authority / executed legal instrument → legal opinion → architecture label`.

### A — Architecture authority
Controls system design.

Priority:
`Canon constraints → controlling architecture meta-layer → PRM-ARCH-DET-002 → ADR → implementation spec`.

### M — Methodological authority
Controls how a specialised method is applied.

Examples:
- AETERNA: actuarial / insurance / reinsurance / capital protection;
- RAVEL operational specification: risk-object execution;
- MRV/scientific methods: measurement and inference.

### I — Implementation-state authority
Controls what is actually deployed.

Priority:
`verified repository/runtime state → implementation declaration → narrative`.

Implementation truth never overrides Canon or law.

### X — Application authority
Controls vertical/domain-specific design.

Examples:
Civilization, Land Regeneration, Rigenera or future profiles.

Application sources are authoritative within scope only if compatible with all superior authorities.

## 2.2 Conflict rule

A source may prevail in one dimension and remain subordinate in another.

Examples:

- a deployed runtime is authoritative for **what code is running**, but not for **what is scientifically true**;
- a valid contract is authoritative for **legal obligations**, but not for **ecological causality**;
- Civilization is authoritative for its application workflow, but not for PROMETHEUS global architecture;
- AETERNA governs actuarial methodology, but does not approve capital.

# 6. D/P/H/Q COMPUTATIONAL CONTRACT

The letters D/P/H/Q describe **computation**, not authority.

## D — Deterministic

Used for:

- schemas;
- hashes;
- state transitions;
- gate logic;
- accounting identities;
- reproducible calculations;
- validation rules;
- release manifests;
- deterministic simulations given frozen inputs and seeds.

Requirement:

same frozen inputs + same versions + same policy → same result.

## P — Probabilistic

Used for:

- Bayesian updating;
- Monte Carlo;
- frequency/severity;
- stochastic cash flows;
- Expected Shortfall / VaR;
- causal uncertainty;
- dependence / tail models.

P outputs must disclose:

- distributions;
- priors;
- parameters;
- calibration;
- horizon;
- seed/reproducibility protocol;
- sensitivity;
- epistemic limits.

Probability never creates evidence.

## H — Heuristic

Used for:

- LLM retrieval/synthesis;
- multi-agent proposal generation;
- red-team;
- hypothesis generation;
- scenario generation;
- architecture search;
- qualitative pattern detection.

H outputs are proposals unless independently verified.

They are labelled:

`HEURISTIC_PROPOSAL` or `LLM_JUDGEMENT`.

## Q — Quantum / Quantum-Inspired

Status by default:

`RESEARCH / SHADOW`.

Potential domains:

- constrained capital allocation;
- combinatorial protection design;
- scenario-set optimisation;
- network partitioning;
- experimental design;
- facility/location optimisation;
- QUBO/Ising-formulated discrete problems.

PROMETHEUS is:

> **QUANTUM-READY, NEVER QUANTUM-DEPENDENT.**

No Q method is admitted merely because it is quantum.

It must beat an appropriate classical baseline on a declared metric such as:

- solution quality;
- computational cost;
- latency;
- energy;
- robustness;
- scalability.

For real quantum hardware, reproducibility means reproducible **protocol and distributional validation**, not falsely requiring identical bit strings.
